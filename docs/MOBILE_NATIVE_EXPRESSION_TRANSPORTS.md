# TIHULU Mobile — native clients, web and Expression Surface

Status: proposed architecture and acceptance plan, not a shipped app or transport. Baseline: PR #134, head 84ef2e602358eb2a2e1fb7e5dbf97a8b62ca000d. Preserve stable application and existing v1–8 clients. No release approval.

## Product experience

One mobile companion family: iOS/iPadOS Swift + SwiftUI (UIKit multi-touch view for stable contact identity), Android Kotlin + Compose (pointer/gesture layer with independent contacts), existing host-served responsive web UI/PWA. Native clients should have feature parity for core performance, not necessarily pixel parity. Landscape and portrait layouts, large targets, left/right handed options, stage lock, local settings and accessible note labels. No mandatory Internet/account. Initial languages follow Studio (verify current locale support; don't claim translations until implemented).

Home: Connect -> Choose instrument -> Play. Scan a host-generated QR or choose a discovered host; explicit pairing. Devices shows named assigned role, connected/armed state and actual transport. Play: Expression, Keys, Pads, XY, Faders, Pedals, Motion. Builder: note/scale assignment, transpose, sensitivity, curve, labels and DAW targets. A permanent release-my-controls action and host Panic are distinct. No output on opening an app or previewing a layout. Warn on unsupported modes; never show unimplemented controls as active.

Phone: single surface, large notes, optional one-thumb Helper. Tablet: larger polyphonic surface, split keyboard + controls, configurable density. Separate owner roles for multiple mobile clients, gamepads, local Trackpad/Magic Mouse, lid and camera. Example: tablet expressive lead, phone wah/expression, controller drums; or two phones controlling separate DAW tracks. Only explicitly shared pedals/effects share destinations. No remote participant grants another participant's permissions.

## Expression Surface

Use Trackpad musical semantics where appropriate, not private macOS touch capture on mobile. Existing CustomScale supports root-relative pitch-class offsets up to +/-49 cents, and StringSurfaceLayout supports bounded custom fret cents and 12/24/53 EDO. These are different models: don't claim arbitrary microtonal grids or full makam/seyir support from CustomScale. UI must disclose which model is selected.

Proposed layout: host-authored stable zone IDs, ordered pitches, root/scale labels, per-zone custom note and optional supported cents offsets, octave window, quantized / glissando / continuous modes. X selects pitch and/or slide; Y optional independently mapped expression/timbre. Choose fixed, attack-derived or supported pressure/area input; contact area is not force or velocity. Devices without pressure keep a fixed default, with explicit optional velocity curve. Avoid fake pressure. Standard MIDI polyphonic note zones can ship first using existing authorized note-mask semantics (up to 25 keys + pedal); rename/reorder regions only via a negotiated/validated host profile, not arbitrary remote MIDI. No independent bends in this compatibility mode. Glissando retriggers with hysteresis; legato continuous pitch is a distinct MPE mode. Per-finger independent pitch, timbre and pressure require a versioned multi-contact stream and safe host MPE member lifecycle. Keep note-off, pedal ownership, retired sustained members, correct RPN range initialization and separate MPE zones/ports. Reject exhaustion without stealing held voices. Never silently quantize requested microtones. Unavailable scale/layout should block expressive mode, not silently substitute a different instrument.

## Transport and trust

Single host authority for assignment, capability negotiation, invitations, disclosure, admission and cleanup. Clients share versioned logical event/profile schemas, golden fixtures and musical semantics; Swift can share suitable pure Swift code with Mac, Android and JS implement the same tested contract. Do not share or duplicate native OS-specific code or create parallel MIDI routing engines for connected mode.

1. LAN first: reuse current Remote TLS invitation and ACK path, existing v7 capability + v8 mapping/label disclosure and conservative workload guard. Inspect actual framing before implementation; use a native transport that interoperates with existing TLS endpoint, or a separately negotiated adapter rather than changing the browser endpoint. Bonjour/mDNS discovery is advisory; QR/manual endpoint fallback. Native iOS uses Network framework/Bonjour with local-network usage disclosure; Android uses NSD and version-appropriate local network permissions. Host TLS identity must be authenticated (trusted certificate or explicitly designed and independently reviewed native QR pinning); never disable TLS verification, trust discovery alone, or embed a persistent secret in a QR. Web retains existing browser trust requirements, no automatic certificate bypass. Hotspot is ordinary local networking when peer connectivity is permitted; don't promise AP isolation bypass.
2. BLE companion: prototype Mac GATT peripheral and iOS/Android central via Core Bluetooth / Android GATT. Verify hardware support, negotiated MTU, write/notify backpressure, OS lifecycle and multiple peers first. Use bounded versioned transport frames, explicit fragmentation limits/timeouts and authenticated application session (review standard authenticated key exchange / AEAD or authenticated secure channel design before production); OS pairing by itself is not permission to play. No custom cryptography. Do not send arbitrary MIDI to Builder. Require host authorization even for paired OS device. BLE and LAN share admission/ownership accounting and the same fail-closed behavior. BLE mode capabilities may be smaller until measured. Never silently fall back to insecure or unversioned input.
3. Optional direct BLE MIDI: separate interoperable output mode using standard BLE MIDI, intended for DAW connection without TIHULU host-mediated gestures. Explicit opt-in, compatible OS/device verification, no duplicate forwarding when companion mode is active; no assumed Builder metadata or host role privileges. Native Android platform MIDI support must be tested by device. Browser BLE is optional only where supported in secure contexts; web LAN is primary.
4. One active performance transport per player session. Switching Wi-Fi/BLE: stop admitting input, release old owned gates/controls, retire epoch, authenticate/admit new session, require neutral/rearm; no held-note carryover or replay. No seamless failover claim until tested. Reconnection never silently binds another player. Explicitly distinguish connected vs ready vs playing vs recovering. No background performance by default; on lock, app suspend, pointer cancellation or permission loss send release if possible, host expiry remains authoritative.

## Capacity and scheduling gates

Baseline has 16 total router sessions, five existing local reservations plus one per mapped gamepad, and at most four authenticated remote peers. Full phone profile may consume seven stream sessions. Current same-kind peers share mappings; independent player roles are not yet implemented. Preserve conservative admission; refuse whole unsupported workload rather than evicting another player. New multi-contact and BLE streams require explicit bounded resource accounting (contacts, MPE channels, message rate, bytes, queue size, CPU) and measured limits before increasing capacity. A connection is not equivalent to one stream. Preserve existing deadlines and release ACK boundary; use bounded edge-first release-aware scheduling, coalesce only replaceable continuous samples; do not merge distinct note edges or replay stale attacks. Host validates finite domains, strict integer/enum fields, frame size, sequence and epoch, capability/role and per-contact ownership before MIDI. No hidden polling or unbounded queue to recover missed taps.

## Incremental implementation gates

A. Freeze and verify #134; add host-generated Expression zone preset using existing note stream and versioned/profile fixtures. Web equal-tempered region mode and explicit limits first. Native Swift client LAN-only proof against existing authenticated protocol: pairing, capabilities, one mapped note, scoped release, neutral/rearm, failure tests. Android mirror consumes same fixtures. Keep native client directories isolated from Studio release build until acceptance.
B. Add full native/web polyphonic zones, layout editing, saved scenes, role assignment. Test touch IDs, same note ownership, glide boundary behavior, resize/rotate, background/lock and wrong metadata. Implement MPE multi-contact wire and allocator only after independent design review.
C. BLE transport adapter proof with physical Mac/iPhone/Android; negotiate reduced capabilities if necessary, then cross-transport session lifecycle. BLE MIDI interoperability separate. Publish measured median/p95/p99 and drop/release counts; ACK RTT is not end-to-end musical latency.
D. Party Jam: mixed native/web/BLE/LAN clients with local Trackpad and two gamepads; actual reservation refusal, independent players, simultaneous controls, shared sustain, mute/disconnect, recorder provenance, recovery. Do not promise four full-profile phones plus every local instrument.
E. Real device accessibility and performance tests, distribution/signing (iOS TestFlight/App Store or authorized development install, Android signed APK/testing), stable-first separate preview, rollback.

Required negative tests: forged/stale/replayed invitation or session, unauthorized role/label access, malformed/truncated/oversized BLE fragments, duplicate event and stale epoch, trust failure, queue exhaustion, touch cancellation or app suspended mid-note, lost release ACK, transport switch with held pedal, two transports competing for one role, insufficient capacity, MPE member exhaustion, partial setup failure. Verify remaining clients and local MIDI are unchanged after every scoped cleanup. Hardware acceptance remains HOLD until actual macOS/iOS/Android devices and DAW are tested.

## Native input validation increment

Swift `MobileLANEndpoint` and Kotlin `MobileLanEndpoint` accept only the host's canonical HTTPS page address (RFC1918 IPv4, port 9444, root path); derive exact WSS :9443, origin and subprotocol. Reject loopback, public/DNS addresses, userinfo, query/fragment, noncanonical octets and wrong ports. Invitations are separate exact 64 ASCII hex characters decoded to 32 binary bytes. No QR secret, persistence, discovery, network call, TLS validation or transport is implemented by these types. A caller must authenticate TLS and verify the negotiated subprotocol before binary invitation delivery; actual admission/capability negotiation and hardware acceptance remain open.

The first native single-family proof now has strict v7 capability decoders in Swift and Kotlin. They accept only a nonempty piano-only family or pedalboard-only family with a continuous lane, reject all extra families, duplicates, noncanonical masks and unsupported manifests, and derive a lane using the exact host mask. This intentionally does not yet support mixed native families or labels. These are pure parsers: actual transport must verify TLS, admission, sequence and neutral ACK separately before enabling performance.

## Single-family native protocol policy

Swift MobileLANSession and Kotlin MobileLanSession now coordinate the single-use connection policy: an independently authenticated current socket with exact subprotocol -> separate binary invitation -> admitted -> v7 capabilities sequence 1 -> selected-family neutral sequence 2 -> accepted -> fresh gestures through the existing sender gate. Optional mapping/label disclosure is not requested (group bridge permits metadata omission); only the group single-family proof is targeted. The adapters must serialize all calls, dispatch each action immediately, route only current-socket responses, poll independently, and close on error or abort. The trustedTLS input is a caller assertion, not TLS validation. No socket or network permission has been added yet. Admission budget 3s; other negotiation ACKs 220ms; existing performance limits retained.
