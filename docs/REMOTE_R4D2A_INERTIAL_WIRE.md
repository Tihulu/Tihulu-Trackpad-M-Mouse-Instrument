# R4d2a — inertial host wire

Adds v3 accelerationArm/acceleration/accelerationRelease and rotationArm/rotation/rotationRelease alongside unchanged v1/v2. Arm/sample require exactly x/y/z numeric components (m/s² gravity-free or deg/s); release has no axes. Existing frame size, pairing, sequence, rate and receipt policy apply. Host validates finite bounded components, computes magnitude, normalizes at 20 m/s² or 360 deg/s, and maps only explicitly configured phone/tablet accelerationMagnitude/rotationMagnitude continuous CC or bend routes. Arm never emits MIDI. Each stream has separate router ownership and 350 ms host freshness, and a sample must follow a prior arm with advancing host time. Idle heartbeat cannot keep any active stream alive. Release affects only that stream, but malformed/stale/replayed frames revoke the whole peer and release its owners. Existing session cap remains; a session allocation failure closes the peer safely. No synthetic sensor data, direct MIDI bytes or client clock.

This is host-side only. Browser DeviceMotion permission and fair multi-stream scheduling are the next increment. No physical motion, rhythm triggering, latency or hardware acceptance claim. No gate routes for magnitude yet; rhythm triggers need explicit retrigger/debounce policy. Stable untouched.
