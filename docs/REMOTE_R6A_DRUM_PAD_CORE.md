# R6a — multi-pad host snapshot foundation

Eight logical drum pad signals (drumPad1–8) and a host-only GM default route factory. V4 drumPads frames carry a complete 8-bit mask (0–255), existing authenticated connection, global sequence/rate/ACK and 256 byte bound. No direct client MIDI numbers or pressure. Host rejects unmapped active bits, disallowed route types and calibration that cannot activate a pad at 1. Each peer has one separate drum router session. A full snapshot adds new owners before releasing old owners; repeated identical snapshots do not retrigger. Zero mask disconnects the drum session only. Shared notes remain held while another owner exists. Separate 350 ms drum freshness; stale data revokes the peer and releases all owners. Other streams cannot refresh it. Stop/Panic and disconnect use existing ownership ledger.

Default routes use GM channel 10 and eight drum notes, velocity 100, customizable host-side. Browser pad UI and explicit host route preset UI are not yet implemented. The planned browser must expose only mapped pad IDs or require a full eight-pad patch, support multiple pointer owners, queue short tap edges safely, send held snapshots and zero on release, and fail closed on backlog. No hardware pressure claims or physical acceptance. Four Swift test scenarios cover simultaneous pads, independent release, shared note transfer, timeout, unmapped mask and schema/route checks. Stable untouched.
