# Touch Instrument / DAW performance

Candidate after #138; hardware acceptance pending. User reports both slow preview and audible DAW interruptions during rapid playing. UI lag alone is not a diagnosis of audio dropouts.

Source findings: existing held fretless contacts run a whole-owner-table set operation per finger plus a final full frame replacement. Unchanged controller/pressure snapshots still perform reconciliation. Reused continuous-pitch channels can unnecessarily emit neutral bend and RPN before the next onset. Changes reconcile only changed targets, update one target directly, defer held-voice bends to the same frame's final reconciliation, and preserve bend ownership through new continuous-pitch onset staging. Pitch and bend-range establishment still precede new note-on. No MIDI sample rate cap, audio buffer change, note-edge coalescing, arbitrary MIDI filtering, or ownership/safety deadline change. Full Swift/SwiftUI implementation.

Diagnostics: constant-space aggregate timing counters between mapped snapshot callback and main-actor entry, and main processing duration. Manual reset/read; no high-rate UI publication or touch/MIDI content storage. Stale/reordered snapshots counted only for current monitor generation. Timing excludes earlier native input processing and downstream DAW/audio. Not proof of hardware-to-sound latency.

Acceptance matrix: fast isolated taps, rapid slides, 2/3/5-finger MPE, held sustain with repeated onsets, Magic Mouse/Trackpad combined, drums, fretted standard MIDI, haptic-only and MIDI-only. Record DAW buffer setting, sample rate, instrument/plugin, CPU/audio overloads, MIDI note-on/off counts and sequence, controller stream counts, and callback timing. Compare same physical hardware and settings to baseline. Test fixed velocity and pressure-to-expression off to distinguish contact-size CC11 attenuation from audio underruns; do not change artistic defaults silently. Check DAW MPE support, configured bend range, feedback routing and audio driver. Test buffer 128/256 as a diagnostic comparison, not a permanent latency workaround.

If queue delays or rejected frames correlate with interruptions, prioritize a bounded ordered, edge-preserving native input lane with explicit failure release; no latest-only musical snapshots. If processing time is small but DAW overloads remain, profile controller delivery and instrument/polyphony, then consider bounded batching or adjustable continuous-controller pacing after independent verification. Swift first for native code; C/C++ or other low-level interop only where measurements/platform APIs justify it, no unnecessary runtime or rewrite.
