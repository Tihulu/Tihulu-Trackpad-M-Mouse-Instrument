# Microtonal keyboard — isolated first increment and UX contract

## Feature intent
Native Mac, iPhone/iPad and Android keyboard surfaces should support classic black/white piano, linear keys, selected-scale keys, microtonal keyboard and custom layouts (isomorphic is a later option). The playable surface is the actual input surface: never duplicate its notes as a second grid merely to make a prototype clickable. A deliberately selected independent chord pad is a different instrument, not duplicate piano controls.

Default classic piano: familiar white/black key hit geometry (black keys win overlap), direct multitouch, optional pitch labels, responsive portrait/landscape/full-screen, configurable visible key count/width. Keep the performance surface primary; compact octave/page and mode selector, optional sustain/pitch bend/modulation, always reachable release/panic. Never display note names as actual receiving pitches when the host only provides logical slot IDs. Linear and scale surfaces remain selectable, not forced on piano users. Controls must work on actual keys, not an auxiliary bank of buttons. Do not claim a simulated chat widget is the app.

## First implementation
MicrotonalKeyboardTuning is an offline Swift core pitch/page model with 2–128 octave-periodic degrees, EDO or custom ordered cents, negative degree indexes, root MIDI anchor and A4 reference 400–480 Hz. Pitch identity is a distinct step, not a nominal MIDI note; 24-EDO has distinct 0/50/100-cent pitches. Pages explicitly map up to 25 authorized logical slots to steps; no protocol change, no MIDI or hardware activation. Current A4 bounds and octave-periodic/MIDI-domain preview are conservative first-increment choices, not universal tuning limits. Native Android parity, classic hit geometry, touch UI tuning selector, persistence, and actual output remain separate work.

## Later feature gates
1. Shared visual/hit-test layout, exact black-key priority, optional labels, configurable visible range; no duplicate note controls. Layout/scale changes only while disarmed or after verified neutral/release.
2. Tuning editor: 12/19/24/31/53 EDO, arbitrary bounded EDO, custom cents/ratios, reference pitch, reviewed makam/comma presets (tuning only, not authentic melodic practice), Scala SCL/KBM import with strict bounds and mapping validation. Non-octave periods and other reference frequencies need separate support.
3. Host-owned frozen pitch-to-slot plan; user explicitly authorizes a tuning and page. Mobile clients send only assigned logical slots; display verified host mapping, do not infer notes from slots. 25 wire slots are not a 25-note scale limit; page transitions need neutral fence and authenticated remapping. No silent 12-TET fallback. Older clients remain standard.
4. True polyphonic microtonal MIDI: dedicated MPE zone with verified receiver bend range, distinct voice identity even for shared anchors, bounded channel pool, deterministic Note Off on original channel and anchor, cleanup debt, sustain/release tails and explicit overflow policy. Per-note MIDI 2.0 or MTS may be separate receiver-specific options. Existing CustomScale ±49-cent model and fixed 15-pitch group plan cannot represent arbitrary EDO; DynamicMPEActivationPlan currently rejects remote, so do not bypass it. Native haptic/local audio frequency path is separate.
5. Independent regression and physical acceptance for actual pitch, quarter-tone polyphony, rapid note edges, old profile compatibility, channel exhaustion, page change with held notes, per-device cleanup, Logic Pro receiver configuration, and portrait/landscape touch ergonomics. No stable activation before acceptance.

## Physical USB MIDI keyboard adapter

The first offline physical-key map preserves original input note identity, and supports three explicit layouts: selected semitone positions (including the older CustomScale cent values), consecutive chromatic hardware keys assigned to consecutive tuning degrees, and white-keys-only scale-degree layout. Off-scale and out-of-domain keys are unmapped/muted in the map. A 24-EDO chromatic layout needs 24 physical semitone steps per sounding octave; it does not pretend an ordinary 12-key octave has 24 independent keys. Input and sounding roots are separate. A macOS scale editor disclosure shows actual black/white physical key positions, mapped versus muted state, selected input note, degree, cents and frequency; it is an offline inspection UI, not live input or MIDI routing. The member pitch encoder includes the A4 reference adjustment for an A4=440 receiver and produces an anchor and 14-bit bend for an explicitly configured bend range. It does not allocate channels or send messages.

Next: explicitly select the exact USB/CoreMIDI source and channel(s), detect physical range or use user calibration, display live held input keys and mapped sounding notes, support user-editable input-to-degree assignment, mute/guide/remap choices and profiles. The existing NativeMIDIMonitor is receive-only and counts packets, not a live routing engine. Implement an isolated native adapter with immutable source identity, bounded input queue, note-on velocity/zero-velocity note-off, physical key+channel ownership, dedicated output port, separate per-voice MPE member allocation including coincident anchors, exact note-off/cleanup debt, sustain and release tails, channel exhaustion without stealing, no input-output feedback or duplicate direct DAW input, hot unplug/stop/panic and no retuning while held. Do not route native MIDI from the offline guide. Physical acceptance needs real USB keyboard, compatible DAW receiver, reference pitch measurement and polyphonic quarter-tone checks. Existing standard MIDI and MPE default-off gates remain unchanged.

For MUSIC-UX: audit physical-key guide accuracy, scale membership versus remapping/muting distinction, color-independent indication, black-key hit priority, range/octave labeling, separate root/transpose controls, current input vs sounding pitch, live status, DAW setup and explicit routing consent. Add this scope to PR #172 review; audit the newer physical adapter candidate separately if original review is pinned.

## Ordinary scale lock
Separate standard 12-TET mapping preserves physical pitches for any tonic. Scale Lock suppresses both note edges for out-of-scale keys rather than snapping them; Scale Guide is non-filtering, Scale Remap is explicit reassignment. The injected-sink single-channel filter tracks held notes and sustain, retains failed cleanup, and never rearms after failure. No native input/output activation yet. Future native adapter must have explicit neutral start, isolated output lane, exact source/channel ownership and no DAW direct-input bypass. Scale edits while playing must release and rearm, not change held notes. Extend to virtual piano/trackpad using the same membership contract; UI must indicate muted versus playable keys with more than color alone.
